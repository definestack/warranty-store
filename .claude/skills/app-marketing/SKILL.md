# App Marketing Content & Assets

Generates two sets of deliverables for the current app, from facts discovered in its own repository:

1. **Website assets** — `docs/website/overview.md`, `docs/website/details.md`, `docs/website/images/`
2. **Google Play Store assets** — `docs/playstore/listing.md`, `docs/playstore/assets/`

Everything here is **app-agnostic**: the `scripts/` directory makes no assumption beyond "an Expo app with `app.json`/`app.config.js` at its root," so it can be copied into another app's repo unchanged. Example commands below use this repo (AtPlace) to illustrate.

## Before you start

- Run this repo's `impact-analysis` skill first, per `CLAUDE.md`. This skill only adds files under `docs/website/` and `docs/playstore/` plus (optionally) running the app in an emulator — it never touches `src/`, schema, or dependencies, so it's normally **Low** severity.
- Never commit on `main`; branch first. Ask before committing, and only once lint/typecheck/tests pass (`.claude/rules/git-commit.md`).
- Preserve any existing files under `docs/` that aren't part of this skill's output — check `discover.mjs`'s `existingOutputs` field and extend rather than overwrite.
- **Never invent** features, platform support, claims, or availability status that isn't backed by something in the repo. If an essential fact can't be confirmed, ask the user instead of guessing.

## Step 1 — Discover

```
node .claude/skills/app-marketing/scripts/discover.mjs --root .
```

This returns the app's identity (name/slug/version/package/scheme/orientation), permissions, icon path, existing docs/ADRs/design references, any screenshots already checked in, existing `docs/website`/`docs/playstore` output, and the list of Expo Router route files.

Then read, at minimum:
- `README.md` and `CLAUDE.md` for the product description, feature list, and target platform.
- `docs/design/` (per `.claude/rules/design-reference.md`, the source of truth for any visual reference).
- The route files under `src/app/**` and their corresponding `src/screens/**`/`src/services/**` to confirm what each screen actually does — don't take a route's filename as a feature description.
- Any ADRs under `docs/adr/` for decisions relevant to what's publishable (e.g. permission usage, platform limitations).

Build a **fact sheet**: one line per claim, each citing the file it came from. Anything you can't cite, don't write down — ask about it instead (see Step 2).

## Step 2 — Ask the user

Before generating anything, ask (one batched question set):

1. **Phone screenshots** — will you supply them (if so, a folder path), or should they be generated by running the app on an emulator?
2. **Feature graphic** — supplied, or generated (composed from the icon + brand colors)?
3. **Tablet screenshots** — skip (default, especially for a portrait-only phone app), generate, or supplied?
4. **Website overview card** — is there a reference screenshot/mockup or an existing website repo to match the layout of? What availability badge (e.g. `COMING SOON`) and CTA text should be used?

Do not proceed past this point assuming generation or assuming supply — always ask.

## Step 3 — Verify current Play Store requirements

`playstore-specs.json` holds the limits this skill validates against, each with a `sourceUrl` and a `verifiedOn` date. **Before generating or validating any Play asset**, fetch each `sourceUrl` and confirm the values still match; if Google has changed a limit, update `playstore-specs.json` (including `verifiedOn`) before continuing. Never generate/validate against stale, unverified numbers.

## Step 4 — Write website content

Start from `templates/overview.md` and `templates/details.md`. Fill only from the Step 1 fact sheet and Step 2 answers.

- Copy the **official icon** — don't generate a replacement. Expo's config declares it (`expo.icon` in `app.json`/`app.config.js`, e.g. `assets/images/icon.png` here) — copy that file to `docs/website/images/app-icon.png`.
- Keep `overview.md`'s description short enough to avoid wrapping (aim ≤160 characters) in the existing card layout.
- Use relative image paths and predictable screenshot filenames (`screenshot-01-<slug>.png`, …).
- `details.md` is for a product landing page, not a technical spec — appropriate depth is features/benefits/audience/CTA, not implementation detail.

## Step 5 — Write the Play Store listing

Start from `templates/listing.md`. It has one `## Heading` per field so `validate.mjs` can parse and check lengths — keep headings as given in the template. Mark anything not inferable from the repo (developer contact email, privacy policy URL) as `TODO` rather than fabricating it. Follow Play policy notes in `playstore-specs.json` (`policy.notes`): no unverifiable superlatives, no competitor references, no keyword stuffing.

## Step 6 — Images

### If the user is supplying images
Run `validate.mjs` (Step 8) on the supplied files first. If they only need format/alpha normalization, use `compose.mjs normalize`. If they violate a hard limit (wrong aspect ratio, oversized), report that to the user and ask before cropping or resizing anything they supplied.

### The Play Store icon
Always generated from the design master, never hand-supplied piecemeal: resize `docs/design/icon.png` (source of truth per `.claude/rules/design-reference.md`) to 512×512.

```
node .claude/skills/app-marketing/scripts/compose.mjs resize-icon \
  --in docs/design/icon.png --out docs/playstore/assets/app-icon.png --size 512
```

### If the user asked you to generate screenshots/feature graphic

Follow the **simulation pipeline** below in order. At each capture, **read the resulting PNG** (it's just a file — use your normal image-reading ability) to confirm it shows the intended screen with no error, toast, or loading spinner, and re-run that shot if it doesn't.

#### 6a. Preflight

```
node .claude/skills/app-marketing/scripts/emulator.mjs doctor
```

Checks `ANDROID_HOME`/`ANDROID_SDK_ROOT`, `adb`, `emulator`, at least one AVD, and Java. If it reports problems, stop and tell the user how to fix them (install Android Studio/SDK, create an AVD, set env vars) rather than guessing around a missing toolchain. Also confirm any app-specific runtime requirement is met — for AtPlace, `GOOGLE_MAPS_API_KEY` must be set (`.env`, see `.env.example`) or the map screen will render blank in screenshots.

#### 6b. Build & install a release build

Use a release variant so screenshots don't show Metro/dev overlays, e.g. `npx expo run:android --variant release` (or install a provided release APK with `adb install`). This step uses the project's own existing build tooling — nothing new to write here.

#### 6c. Boot and prepare

```
node .claude/skills/app-marketing/scripts/emulator.mjs boot --avd <name>
node .claude/skills/app-marketing/scripts/emulator.mjs prepare --package <android.package> --serial <serial>
```

`boot` waits for the device to finish booting and prints its `serial`. `prepare` grants the runtime permissions the app declares (from `discover.mjs`'s `androidPermissions`), turns on system UI demo mode (clean status bar: 12:00, full battery/signal, no notification icons), and disables animations so captures are deterministic.

#### 6d. Seed realistic, clearly fictional sample data

Use the app's **own import/deep-link/UI path** — never write to its database or storage directly. For AtPlace: build a backup JSON matching the `BackupPayload` shape in `src/services/backup.ts` (`version: 1`, `places`, `reminders`, `settings`), with a few clearly fictional sample places and reminders (e.g. "Home" / "Buy groceries", "Work" / "Take badge"), `adb push` it to `/sdcard/Download/atplace-backup.json`, then drive Settings → Backup & Restore → Import through `capture.mjs`-style taps (see Step 6e). For a different app, use whatever its own import/seed mechanism is — the principle generalizes, the mechanism doesn't.

Set a plausible mock location so any map/geofence screen shows something real:

```
node .claude/skills/app-marketing/scripts/emulator.mjs geo --lat <n> --lon <n> --serial <serial>
```

#### 6e. Define the shot list

Write `docs/playstore/capture/shots.json` (kept under version control so later runs can reproduce the same shots). Schema and examples are documented in `capture.mjs`'s header comment. Aim for 4–8 shots, each showing a distinct feature — don't shoot the same screen twice. For AtPlace, reasonable shots: reminders list (home), map with a place/geofence, add-reminder form, place detail, a real triggered notification (use the app's own test-notification feature in Settings, not a mock-up), and one dark-mode shot (`"theme": "dark"`). Navigate by deep link where the route supports it (`<scheme>://<route>`, e.g. `atplace://(tabs)/home` — `scheme` comes from `discover.mjs`) or by `tap`/`back` steps matched by text/content-desc/resource-id (never hard-coded coordinates, so shots survive layout changes).

#### 6f. Capture

```
node .claude/skills/app-marketing/scripts/capture.mjs \
  --shots docs/playstore/capture/shots.json \
  --out docs/playstore/assets/screenshots/phone \
  --serial <serial>
```

Read each resulting PNG before moving on. Re-run a specific shot (edit `shots.json`, re-run `capture.mjs`) if it doesn't look right.

**Check the aspect ratio before validating.** Many devices (e.g. a Pixel 7 at 1080×2400, 20:9) are taller than Play's "long side ≤ 2× short side" screenshot rule allows — `validate.mjs` will flag this. Fix it by **padding** the short side (never cropping — that loses real UI, like the footer tab bar), filling the new canvas with the screenshot's own background color so the border is unnoticeable:

```
node -e '
import("jimp").then(async ({Jimp}) => {
  const path = "<screenshot file>";
  const img = await Jimp.read(path);
  const target = Math.ceil(img.bitmap.height / 2); // long side / 2, Play's exact limit
  if (img.bitmap.width >= target) return;
  const bg = 0xfaf6f0ff; // the screenshot's own background color, 0xRRGGBBAA
  const canvas = new Jimp({ width: target, height: img.bitmap.height, color: bg });
  canvas.composite(img, Math.round((target - img.bitmap.width) / 2), 0);
  await canvas.write(path);
});
'
```

Copy the chosen subset into `docs/website/images/` with the predictable `screenshot-NN-<slug>.png` naming from Step 4.

#### 6g. Feature graphic

```
node .claude/skills/app-marketing/scripts/compose.mjs feature-graphic \
  --out docs/playstore/assets/feature-graphic.png \
  --name "<App Name>" --tagline "<tagline>" \
  --icon docs/design/icon.png --background "<brand hex>"
```

Brand background/colors come from `app.config.js` (e.g. the adaptive-icon background color) or `src/theme/colors.ts`-style token files if present — never an invented palette. This only composes the icon/name/tagline on a brand-colored canvas; it never fabricates UI.

Optionally, caption a real screenshot for the website or store listing with `compose.mjs frame --in <screenshot> --out <file> --caption "<text>"` — the screenshot's own pixels are never altered, only framed.

#### 6h. Teardown

```
node .claude/skills/app-marketing/scripts/emulator.mjs teardown --serial <serial>
```

Restores demo mode and animation settings. The AVD is left running unless `--kill` is passed — don't kill a device the user didn't ask you to tear down.

## Step 7 — Organize deliverables

```
docs/
  website/
    overview.md
    details.md
    images/
      app-icon.png
      screenshot-01-<slug>.png
      ...
  playstore/
    listing.md
    capture/
      shots.json
    assets/
      app-icon.png
      feature-graphic.png
      screenshots/
        phone/
        tablet/        (only if generated/supplied)
```

Don't touch unrelated existing files under `docs/` (e.g. `docs/adr/`, `docs/design/`).

## Step 8 — Validate

```
node .claude/skills/app-marketing/scripts/validate.mjs \
  --specs .claude/skills/app-marketing/playstore-specs.json \
  --icon docs/playstore/assets/app-icon.png \
  --feature-graphic docs/playstore/assets/feature-graphic.png \
  --phone-screenshots docs/playstore/assets/screenshots/phone \
  --listing docs/playstore/listing.md
```

Fix anything reported and re-run until every check passes. Then report back to the user: files written, key assumptions made, any `TODO`s left in `listing.md`, and anything that still needs manual action in Play Console (e.g. content rating questionnaire, pricing/distribution, data-safety form — none of which this skill can determine from the repo).

## Git

Branch off `main` (never commit directly on it), conventional commit message, lint/typecheck/tests passing, and ask before committing — per `.claude/rules/git-commit.md`.
